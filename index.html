the scale-up launch kit

0. The brief

Goal for the next 90 days: turn Agentic Batch Changes (ABC) from a GA announcement into a repeatable pipeline motion: more accounts running their first fleet-wide change, more merged changesets per account, and a story the field can tell in five minutes.

Why this launch matters now

  • The inner loop got fast; the outer loop didn't. Coding agents made single-repo work cheap. Fleet-wide work (CVE fixes, dependency upgrades with breaking changes, end-of-life deadlines) is still tickets, spreadsheets and chasing owners across hundreds of repos.
  • Self-hosted is now live. ABC shipped to self-hosted customers with Sourcegraph 8.0 on 16 September 2026, which opens the regulated and security-conscious accounts that run Sourcegraph on their own infrastructure.
  • Pricing is a story, not a footnote. Paying only for merged changesets lowers the risk of trying it and aligns spend with outcomes. Few AI tools can say that.
  • The product keeps moving. On 28 September ABC moved to a Sourcegraph-managed coding agent with MCP and Finder, Oracle and Worker subagents, while existing batch specs stay compatible. Messaging has to keep pace with a fast-changing product.

Three bets this kit makes

1. Own the category word

Name the problem as fleet-wide change, the outer loop of software. Coding agents own the inner loop; Sourcegraph owns everything that spans repos.

2. Lead with security, expand with migrations

CVE remediation has urgency, a budget owner and a deadline. It is the fastest first win, and migrations become the expansion.

3. Sell trust, not autonomy

Engineers distrust "autonomous refactoring". They trust plans, CI-healthy diffs and their own approval on every changeset.

1. Market & competition

Buyers will compare ABC with what they already have, not with a category map. The honest frame is: each alternative is good at part of the job; ABC is built for the whole job across the whole codebase.

Competitive rule for the field: never claim a competitor "can't" do something. Say what ABC does and let the buyer compare. Engineers check claims, and one wrong claim costs the whole deal its credibility.

3. Positioning & messaging

Positioning statement

For platform and security teams at large engineering organisations who must make the same change across hundreds or thousands of repositories, Agentic Batch Changes is the agent for fleet-wide change. Unlike single-repo coding agents or recipe-only refactoring tools, it uses Sourcegraph's understanding of the entire codebase to plan the change, applies it with a script or with judgment as each repo needs, keeps going until CI passes, and leaves every merge to a human, so you pay only for changes that ship.

Messaging house

Umbrella message

Describe the change once. Ship it everywhere it needs to go, with your engineers approving every diff.

pillar 1 · scope

See every place the change applies

Built on Sourcegraph's index of all your code. Deep Search and Code Search find every affected repo and build the plan before any code changes.

pillar 2 · execute

Change code with judgment, not find-and-replace

Scripts for deterministic changes, a coding agent for changes that need judgment. Validated on one repo first, then fanned out. Reads CI logs, fixes failures, resolves conflicts.

pillar 3 · control

Stay in control, pay for outcomes

Engineers review and approve every changeset. Merge status for every PR in one place. Billed per changeset merged, never for PRs you decline.

3b. Messaging audit of today's ABC page

I read the current Agentic Batch Changes page and the homepage as a first-time enterprise buyer would. The foundation is strong. These are the gaps I would close first, in priority order.

What already works

  • "One migration. Every repository." is a sharp, ownable hero.
  • The plan → scope → execute → publish → verify pipeline explains the product in five words.
  • "Pay per changeset merged, not per token, seat, or attempt" is a rare, credible differentiator.
  • Scripts vs coding agents is explained honestly, which earns developer trust.

Where buyers will still hesitate

  • Security buyers don't see themselves: CVE remediation is one item in a list of 13 migration examples, even though the lead customer story (Mercari) is a security fix.
  • "Why not just use our coding agent?" is the first question every visitor with Copilot or Claude Code will have, and the page doesn't answer it directly.
  • The proof has no numbers on the page: the quotes don't carry Mercari's ~80 repos or Canva's 50+ merged PRs, which are in the press release.
  • The closing line names Sourcegraph Cloud only; self-hosted availability with 8.0 isn't mentioned, so the most regulated buyers may assume it isn't for them.
  • There's no FAQ, so cost, data handling and "what counts as a changeset" questions go to sales instead of being answered on the page.

4. How it works & the demo

The technical story is the sales story. This is the flow I would put in the launch blog, the docs overview and the first demo slide, built from the public changelog (14 and 28 Sept 2026).

Technical proof points engineers will ask about

QuestionAnswer we can show
How does it know which repos to change?The coordinator uses Sourcegraph Code Search and Deep Search across the indexed codebase. Deep Search runs an agentic search loop, returns cited sources and can export large analyses as CSV or JSON.
Is every change written by an LLM?No. Each part of the plan gets a script when the change is deterministic and a coding agent only when judgment is needed.
What happens when CI fails?It reads the CI logs, pushes follow-up commits and asks a coding agent to resolve merge conflicts. It stops and asks when it's stuck.
Can it follow our repo conventions?Yes: skills and AGENTS.md-style guidance at user, org or global level. Attribution can live in commit trailers only (batchChanges.attributionMode: trailerOnly).
Will our existing work break?Existing batch specs remain compatible after the move to the Sourcegraph-managed coding agent.
Can our own agents use the same context?Yes. The Sourcegraph MCP server (GA Feb 2026) exposes search, navigation, history and Deep Search tools to Claude Code, Codex, Cursor, Copilot, Amp and others, with OAuth and an mcp scope.
Where does it run?Sourcegraph Cloud, and self-hosted from Sourcegraph 8.0.

The demo inputs, ready to run

A demo is only as credible as its prompt. This is the prompt and repo guidance I would give the agent, based on GitHub's own hardening advice for Actions: pass untrusted event data through an environment variable instead of interpolating it into a shell script.

Prompt to Agentic Batch Changes

Find every GitHub Actions workflow in our org that
interpolates untrusted event data directly into a
`run:` script, for example:

  run: echo "${{ github.event.issue.title }}"
  run: git checkout ${{ github.head_ref }}

For each one, move the value into a step-level `env:`
variable and reference it as "$VAR" inside the script.
Do not change workflow behaviour otherwise.

Pilot on platform/ci-templates first. Skip archived
repos. Open one changeset per repo with a short
description linking to the security advisory.

AGENTS.md guidance (org level)

# Conventions for automated changes

- Keep diffs minimal. No formatting-only edits.
- Workflows: quote all shell variables ("$VAR").
- Never add new third-party actions; pin existing
  ones by commit SHA if you touch them.
- Changeset title: "security: <short summary>".
- Link the advisory ID in the description.
- If CI fails for reasons unrelated to the change,
  stop and ask instead of "fixing" other code.

The before and after for one workflow step:

# before: untrusted title is expanded into the shell script
- run: echo "New issue: ${{ github.event.issue.title }}"

# after: the value reaches the script only as data
- env:
    ISSUE_TITLE: ${{ github.event.issue.title }}
  run: echo "New issue: $ISSUE_TITLE"

Launch blog draft (opening, ready to edit)

Headline options

  • The outer loop finally has an agent
  • Found once, fixed everywhere: fleet-wide change for enterprise codebases

Opening

Coding agents made the inner loop fast. You can fix a bug or ship a feature in one repository in minutes. But the work that slows engineering organisations down rarely lives in one repository. It is the dependency upgrade that breaks in 300 services, the vulnerable pattern copied into 80 workflows, the end-of-life deadline nobody owns.

Agentic Batch Changes is built for that outer loop. Describe the change once. The agent finds every repository it applies to, tries it on one first, then rolls it out with a script where the change is mechanical and a coding agent where it needs judgment. It reads your CI logs, fixes what breaks and tracks every changeset to merge. Your engineers approve every diff, and you pay only for the changes that merge.

6. Sales enablement

Five-minute talk track

  1. Problem: "How long did your last org-wide upgrade take, and who had to chase the teams?"
  2. Shift: "AI made writing code in one repo fast. Changing code across all of them is still manual."
  3. Answer: "Agentic Batch Changes plans the change across your whole codebase, applies it with a script or an agent as each repo needs, and keeps going until CI passes."
  4. Trust: "Your engineers approve every changeset, and you pay only for the ones that merge."
  5. Proof and ask: "Mercari patched a GitHub Actions vulnerability across about 80 repos. What's the change on your backlog nobody wants to own? Let's run it."

Discovery questions

Size the pain

  • How many repos and code hosts do you have?
  • What org-wide change is overdue right now?
  • How long did the last one take, and how many teams touched it?
  • How do you track progress today?

Find the urgency

  • Any open CVEs or audit findings across many repos?
  • Upcoming end-of-life dates for runtimes, libraries or CI?
  • Who gets blamed when it slips?
  • Is there a mandate or deadline from leadership?

Qualify the fit

  • Are you on Sourcegraph Cloud or self-hosted, and which version?
  • Which CI systems do you use?
  • Do you already use Batch Changes or coding agents?
  • Who reviews automated PRs today?

Map the buying group

  • Who owns platform and developer experience?
  • Does security fund remediation tooling?
  • What does AI tool approval look like?
  • Who signs for usage-based spend?

ROI model for the business case

Every number below is an input the customer changes. The defaults are illustrative only.

—engineer hours returned per year
—labour cost avoided per year (before ABC cost)
—repo-weeks of exposure per change, today

Formula: (manual hours − review hours) × repos × changes per year. Exposure = repos × calendar weeks, a simple way to show security risk that stays open while a manual fix rolls out. Subtract ABC cost (changesets merged × the customer's credit rate) for net value.
